# AI 账号商家经营日报拆分与融合分析

日期：2026-09-01  
时区：Asia/Shanghai  
涉及站点：`news.aivora.cn`、`supply.aivora.cn`、`yuyu.aivora.cn`

## 1. 结论

AI 账号商家经营日报应从 AI 日报的产品边界中彻底拆出，并由货源站承担唯一正式入口、正文、归档和搜索引擎 canonical。AI 日报只保留旧网址迁移能力，不再展示日报正文，也不再在导航、首页、搜索、站点地图或 LLM 说明中向买家推荐货源入口。个人主页作为中立的项目门户，为卖家提供“AI 货源与商家经营”入口。

这不是简单移动一个菜单，而是要同时拆开五条耦合：内容生成、GitHub 发布目标、货源站采集、页面归属、受众入口。只改页面会让后台继续把内容写回 AI 日报；只改后台会造成旧链接、历史归档和搜索权重丢失。

## 2. 当前事实与根因

### 2.1 当前内容已经货源化，但产品归属没有迁移

后端账号日报已使用 `supply.aivora.cn/api/opportunities/snapshot`，依据标准商品、可购买报价、库存、价格异动和暂停接单清单生成，当前流水线标识为 `supply-merchant-daily-v2`，生成过程不调用大模型。

问题在发布端：Worker 仍使用 AI 日报的全局 GitHub 目标，把 Markdown 写入 `Hextra-AI-Insight-Daily/content/cn/account-opportunity/`。货源 V1 又从这个目录抓取，V2 再从 V1 导入 Supabase，形成以下反向依赖：

```text
货源快照
  -> AI 日报 Worker 生成账号经营日报
  -> 写入 AI 日报仓库
  -> AI 日报公开展示给买家
  -> 货源 V1 反向抓取
  -> 货源 V2/Supabase 再展示
```

因此内容主题虽已改变，所有权仍在 AI 日报，买家仍能从 AI 日报首页、主导航、搜索和旧正文进入第三方货源。

### 2.2 受众冲突

| 站点 | 第一受众 | 第一任务 | 不应出现的内容 |
| --- | --- | --- | --- |
| AI 日报 | 爱窝啦店铺买家、AI 资讯读者 | 获得可信 AI 资讯与店铺服务 | 第三方货源报价、卖家采购路径、备货与停单建议 |
| 货源站 | AI 账号卖家、采购者 | 找货、比价、核库存、算利润、决定接单 | 与当前货源无关的泛新闻堆积 |
| 个人主页 | 关注作者及全部项目的人 | 按需求进入不同项目 | 把买家入口和卖家入口混成同一个产品 |

AI 日报中的账号经营栏目会把买家直接带到采购侧，既破坏购买路径，也让“资讯站”和“卖家工具”的品牌承诺相互冲突。

### 2.3 历史数据与 URL 风险

AI 日报仓库现有 134 期账号日报，约 0.89 MB。直接删除会造成旧链接失效、搜索引擎重复或丢失收录、外部链接断裂；继续保留正文则不算真正拆分。

正确做法是：先把完整历史源文件迁到货源仓库并导入 Supabase，再将 AI 日报中的正文替换成轻量迁移页。旧日期与新日期保持一一映射：

```text
旧：/account-opportunity/2026-08/2026-08-31/
新：/opportunities/2026-08-31
```

GitHub Pages 不能配置真正的服务器端 301，所以第一阶段使用 `noindex`、新站 canonical、零秒 meta refresh 和 JavaScript replace；若未来把 `news.aivora.cn` 接入可编程边缘层，再升级为 HTTP 308。

### 2.4 货源站现有融合不足

货源站已有实时经营台和日报详情，但仍存在四个结构性缺口：

1. 首页只展示最近 12 期，数据读取上限为 100，没有完整归档和分页入口。
2. 日报详情仍显示“查看日报原页”，把用户送回 AI 日报，canonical 归属和用户闭环相互矛盾。
3. 历史 `source_url` 仍指向 `news.aivora.cn`；迁移后应统一为货源站对应日期。
4. V1 的默认源仓库与 dry-run 仍指向 AI 日报，未来日报仍会形成反向依赖。

## 3. 目标信息架构

```text
yuyu.aivora.cn
  ├─ AI 日报（买家与资讯） -> news.aivora.cn
  ├─ AI 货源与商家经营（卖家） -> supply.aivora.cn
  └─ 其他项目

news.aivora.cn
  ├─ AI 日报
  ├─ AI 时间线
  ├─ AI 商机
  └─ 旧账号日报 URL -> 对应 supply 日期（只迁移，不曝光）

supply.aivora.cn
  ├─ 商品分类与货源详情
  ├─ 渠道、价格、库存异动
  ├─ 利润计算器
  └─ 商家经营台
      ├─ 今日实时货源信号
      ├─ 最新经营日报
      ├─ 完整日报归档
      └─ 单期日报 + 当前相关货源 + 利润动作
```

## 4. 内容与经营闭环

日报在货源站的职责不是“再做一份新闻”，而是把实时盘面压缩成卖家当天能执行的清单：

1. 从库存、可购买报价、最低进货参考和连续快照异动判断“今天先看什么”。
2. 每个核心商品必须回链到标准商品页，采购前核对原始渠道、规格、交付和售后。
3. 每个可接单方向都给出利润计算入口；不以低价、渠道数量或新闻热度冒充销量和利润。
4. 完全缺货、规格不清、售后不可核验或售价低于保本价时明确停止。
5. 官方价格、额度、政策和支付变化只作为辅助证据，不能覆盖实时货源事实。

这会形成完整链路：

```text
实时采集 -> 标准商品归一 -> 库存/价格信号 -> 经营日报
        -> 商品核验 -> 利润测算 -> 小量接单 -> 异动复查
```

## 5. 数据所有权与稳定边界

### 5.1 数据所有权

- Worker 生成算法仍留在 `CloudFlare-AI-Insight-Daily`，以避免重写稳定流水线。
- AI 日报主体继续写入 `Hextra-AI-Insight-Daily`。
- 账号商家经营日报使用独立目标变量，写入 `Aivora-Supply-Radar`。
- 货源 V1 从本仓库读取日报源文件；V2 将其导入 Supabase并提供正式页面。
- AI 日报不再承担账号日报的内容存储，只保留旧 URL 迁移桩。

### 5.2 稳定边界

- 账号日报写入货源仓库失败只能标记账号日报失败，不能阻塞 AI 日报主体。
- 不改 `DAILY_ANTHROPIC_MAX_TOKENS`、日报 repair、FAQ 或 AI 日报生成逻辑。
- 不把第三方货源入口重新加回 AI 日报。
- 不删除历史期数；先复制、校验数量与哈希，再替换旧站正文。
- 日报生成仍保持 0 次模型调用；迁移只增加 GitHub 目标切换与一次 Supabase 归档同步。

## 6. SEO、GEO 与跳转策略

### 新站

- `/opportunities` 是商家经营台 canonical。
- `/opportunities/YYYY-MM-DD` 是单期日报 canonical。
- `/opportunities/archive` 提供分页归档。
- sitemap 收录经营台、归档和全部已迁移日报。
- 日报详情保留 Article/BlogPosting 时间信息，由货源站统一承接搜索权重。

### 旧站

- 删除主导航、首页快捷入口和 `llms.txt` 中的账号经营链接。
- 账号栏目和所有日期页设置 `noindex`，从 sitemap 与站内搜索排除。
- 每个旧日期页 canonical 到对应新日期并立即跳转。
- 旧正文不继续渲染，避免买家阅读或搜索引擎判定重复内容。

## 7. 成功标准

1. AI 日报首页、主导航、搜索数据和 `llms.txt` 不再出现账号经营入口。
2. 任意旧日期链接都能跳到货源站同一天，而非笼统跳首页。
3. 货源站能打开最新经营台、完整分页归档和历史详情。
4. 历史 134 期源文件全部进入货源仓库，迁移脚本能导入 Supabase。
5. 下一期 Worker 只把账号日报写入货源仓库，AI 日报仓库不再新增正文。
6. 个人主页在首页项目区、项目页、顶部导航和页脚提供明确的卖家入口。
7. AI 日报主体测试、Hugo 构建和线上最新日报均不受影响。
8. 桌面与约 390px 手机视口、日间与夜间模式无溢出、跳变或错误链接。

## 8. 风险与回滚

| 风险 | 控制 | 回滚 |
| --- | --- | --- |
| Worker GitHub Token 无权写货源仓库 | 部署前用只读/测试流程验证目标配置；生产最多触发一次 | 回滚后端目标提交，不改 AI 日报主体 |
| 历史归档未完整进入 Supabase | 迁移脚本按 GitHub 文件 SHA 幂等 upsert，并输出发现、更新、跳过数量 | 重跑归档工作流 |
| GitHub Pages 无 HTTP 301 | canonical + noindex + meta/JS 跳转，保留明确链接 | 回滚 AI 日报迁移页提交 |
| 新站部署失败 | 先完成 V2 完整构建和隔离 Worker 验证，再切边缘绑定 | 使用现有 V1 自动回滚流程 |
| 账号任务失败影响主日报 | 保留 `runIsolatedAccountOpportunity` | 回滚后端提交，主体日报无需回滚 |

## 9. 上线后边缘运行时风险与修正

最终验收发现，V2 并非持续不可用，而是在 SEA 边缘节点间歇返回 Cloudflare 1101。连续请求对照和 Worker Tail 给出了相同结论：主页失败事件为 `outcome=exceededCpu`、CPU 约 10 ms；日报详情失败事件同样为 `exceededCpu`、CPU 约 93 ms。IAD 节点同期 36 次请求全部成功，说明问题与节点执行预算和 SSR 路径有关，不是 Supabase 数据缺失、域名解析错误或日报迁移失败。

当前 Cloudflare Workers 免费套餐的每次请求 CPU 上限为 10 ms。OpenNext SSR 的正常执行时间会随页面、节点和冷启动状态波动，因此仅靠“重新部署同一 Worker”不能消除故障；把 `cpu_ms` 写进 Wrangler 也无法在免费套餐上突破上限。直接升级付费套餐可以提高上限，但涉及新增费用，不应在未获授权时自动购买。

本次采用不增加费用的边缘韧性层：

1. Pages 域名入口只缓存无 Cookie、无 Authorization 的公开 GET HTML/XML/文本响应，绝不缓存管理请求或公开 JSON API。
2. 最近 5 分钟的成功页面直接由边缘缓存返回，避免重复进入 SSR；成功副本最长保留 24 小时，只在上游失败时作为陈旧可用副本。
3. GET/HEAD 遇到 500、502、503、504 或服务绑定异常时最多重试 4 次；POST 等写操作只执行一次，防止重复写入。
4. V2 多次失败且没有缓存时，仅对旧站确实存在的只读页面尝试 V1 服务兜底；不把 V2 API 转发到不兼容的 V1 API。
5. 所有兜底都失败时返回带 `Retry-After` 的品牌化 503，而不是 Cloudflare 1101；该页面 `noindex`、`no-store`，不会污染收录和缓存。
6. 响应用 `X-Aivora-Edge-Cache` 标记 `HIT/MISS/BYPASS/STALE/LEGACY/UNAVAILABLE`，部署验收连续检查关键路径，便于区分正常缓存、陈旧兜底和真正故障。

这个方案优先保证买家可访问和日报可读，同时保留 V2 功能。长期最干净的方案仍是把生产 Worker 升级到可配置 CPU 的付费套餐，或把高成本页面预渲染为静态 HTML；两者都应作为后续独立变更评估，而不是混入本次内容拆分。
